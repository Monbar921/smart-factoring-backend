# SMF-33. Архитектурные решения (предложения, на согласовании)

Статус: **черновик** — каждое решение помечено, утверждено или нет. Утверждённые переносим в «Принято».

## Предлагаемые решения

**Р-1. Прогон пересчитывает блоки 2–5 целиком на срезе даты расчёта.**
ПР-4 говорит об инкрементальной обработке «с предыдущего прогона», но ПР-9 требует перестраивать блоки 2–3 при дате назад,
а НФР-5 — детерминизм. На объёме 1 500 УПД полный пересчёт стоит секунды. Инкрементальной делаем только загрузку (блок 1,
идемпотентно по ключу «номер + дата + ИНН клиента»). Это проще и автоматически даёт К-15.

**Р-2. Хранилище данных ручной загрузки и имитации источников — в backend, таблицы `manual_upload_*` в схеме приложения.**
Адаптеры за интерфейсами (`EdoSource`, `BankStatementSource`, `CounterpartyDataSource`, `FactoringReceiver`, `RiskReceiver`)
читают/пишут таблицы `manual_upload_*`. Замена на интеграцию = новая реализация интерфейса (ДД-1). Наполнение `manual_upload_*` — импорт выгрузки
генератора из smart-factoring-ml (CSV/Parquet) отдельной командой/эндпоинтом.

**Р-3. Сервис моделей — FastAPI в smart-factoring-ml, batch-эндпоинты.**
`POST /pd/score` (список покупателей → PD, базовый/модельный, 3 причины SHAP, версия) и `POST /delay/score` (список УПД
с признаками → P(delay>14), P(90+), ожидаемые дни, версия). Батчи вместо вызова на каждый УПД — укладываемся в НФР-1.2.
Контракт (OpenAPI) фиксируем до обучения моделей, сначала поднимаем **заглушку** с детерминированными ответами —
backend не ждёт ML.

**Р-4. Решающая логика (блоки 2, 3, 5) — чистые Java-функции без Spring/БД.**
Покрываем юнит-тестами по примерам BRD (п. 5.1, деление лимита п. 5.3, таблица TR) и контрольным случаям.

**Р-5. Один прогон за раз — частичный уникальный индекс** `run(status) where status = 'RUNNING'` + проверка в сервисе.
Выполнение асинхронное (свой executor), шаги последовательно, внутри шага УПД параллельно.

**Р-6. Ход прогона на UI — polling раз в 2–3 с** (`GET /runs/{id}`), без SSE/WebSocket через gateway. Требование ЭП-2 — не реже 5 с.

**Р-7. Детерминизм и LLM.** LLM влияет только на тексты. Тексты кешируем по хешу входа (причины + язык), чтобы повторный
прогон не дёргал LLM и давал те же карточки. Без LLM — карточка без черновика (п. 5.3).

**Р-8. Роли Keycloak:** `operator` (экран процесса), `manager` (эмулятор CRM). В демо менеджер выбирается из списка (НФР-9),
фильтрация «только свои клиенты» — по выбранному менеджеру, не по токену.

**Р-9. Параметры Приложения А — в таблице `parameter`** (с дефолтами из Liquibase), читаются в начале прогона
и снимком сохраняются в прогоне (воспроизводимость).

**Р-10. Структура backend:** новые maven-модули в `feature/`: `run-service` (оркестрация + блоки 1–5),
`decision-service` (блок 6, очередь, карточка), `demo-source` (имитации и импорт), `ml-client`, `llm-client`;
REST-контроллеры — в `ui-service` (как сейчас `MaintenanceController`).

## Принято (25.10.2026, по ответам в 04-open-questions.md)

- **Р-1** полный пересчёт блоков 2–5 — принято.
- **Р-3** сервис моделей отдельным контейнером — принято; контейнер добавляется в `smart-factoring-deploy`.
- **Р-11. Разделение работ.** Коллега делает: модели PD и задержки (обучение, проверка), генератор синтетики
  с контрольными случаями, промпты и тексты для LLM, презентацию. Мы делаем: backend, gateway, UI, контракты
  (backend ↔ сервис моделей, формат выгрузки генератора → импорт), адаптер LLM (без содержательных промптов).
- **Р-12. LLM — GigaChat**, ключа пока нет. Адаптер с переключаемой реализацией: `gigachat` / `stub`
  (детерминированные шаблонные тексты) / `off` (карточка без черновика).
- **Р-13. Уровни риска до модели PD:** A < 1%, B < 3%, C < 8%, D ≥ 8% — параметры, заменяются по итогам модели.
- **Р-14. Базовый PD («мало данных») считает сервис моделей**, backend получает PD и флаг.
- **Р-15. «Кассовый разрыв» в карточке клиента** = сумма неоплаченных остатков УПД в кат. 5–8,
  показывается, если абсолютная ликвидность клиента < 0,2.
- **Р-16. «Новое в прогоне»** = предложение в очереди, по УПД которого в предыдущем успешном прогоне
  предложения в очереди не было (включая ранее отозванное и вернувшееся после смены даты расчёта назад).
  Первый прогон — все предложения новые.
- **Р-17. В демо один менеджер**, все клиенты за ним. Модель данных всё равно держит связь клиент → менеджер.
- **Р-18. Снимок ЕГРЮЛ/ЕФРСБ** — файл `efrsb_out/events.csv` (событийная выгрузка по ИНН: статус ЕГРЮЛ с датой,
  дело о банкротстве со стадиями, события). Backend импортирует его в таблицы `manual_upload_*`: стоп-фактор по ЕГРЮЛ-статусу
  и стадии дела на дату снимка (п. 4.1, ДД-6). Отчётность ГИР БО нужна только для PD — её держит сервис моделей.
- **Р-19. Сервис инференса делаем мы** (FastAPI в smart-factoring-ml): сначала заглушка, потом подключаем артефакты
  моделей коллеги. Коллега отдаёт обученные модели и промпты LLM, мы их встраиваем.
- **Р-20. Внешние данные по покупателям (ГИР БО, ЕГРЮЛ, ЕФРСБ) хранит backend** в таблицах `manual_upload_*`, как требует п. 1.3 и C4
  («снимок открытых данных» в хранилище данных ручной загрузки). Сервис моделей stateless: backend передаёт ему ИНН вместе с отчётностью
  и профилем. Так схема не зависит от того, в каком виде коллега отдаст ГИР БО. Заменяет вторую половину Р-18.
- **Р-21. Для модулей и тестов берём корневой `efrsb_out/events.csv`.** Покупатель без строк в файле = событий нет;
  «нет данных по покупателю» определяется отсутствием ИНН в реестре покупателей (п. 1.4).
- **`.env` не трогаем** (ответ на вопрос 17).
- **Р-22. В сервис моделей передаём сырые данные** (отчётность, профиль, УПД, история оплат); признаки считает сервис
  тем же кодом, что при обучении.
- **Р-23. Результаты храним по прогонам** (`run_id` в таблицах результатов); между прогонами живёт только `offer`.
- **Р-25. Одна схема БД `smart_factoring_test`** (через `POSTGRES_SCHEMA`), создаётся на стенде заранее.
  Отдельной схемы `demo` нет: таблицы источников и имитаций — в ней же, с префиксом (меняет Р-2; с Р-56 — `manual_upload_*` и `imitation_*`). В тестах схему создаёт init-скрипт контейнера.
- **Р-26. Доступ к данным — Spring `JdbcClient`, без JPA-сущностей.** Результаты прогона пишутся пачками
  (~1 500 строк на таблицу), детализация и воронка — SQL-отчёты; сущности тут только мешают. JPA-стартер из `common` не трогаем.
- **Р-27. Код backend:** один feature-модуль `feature/factoring-service` (пакеты `run`, `parameter`, `source`, `load`,
  `reconciliation`, `categorization`, `scoring`, `decision`, `offer`, `ml`, `llm`), контроллеры — в `ui-service`,
  DTO API — в `smart-factoring-backend-api`. Делить на несколько maven-модулей нет смысла: всё в одном процессе.
- **Р-28. Прогон прерван перезапуском backend** → при старте приложения прогоны `RUNNING` переводятся в `STOPPED`
  с причиной в журнале; иначе индекс «один прогон» заблокировал бы запуск навсегда.
- **Р-29. Набор клиентов прогона — по ИНН** (`StartRunRequest.clientInns`, колонка `run.client_inns`): до первой
  загрузки клиентов нет в основной таблице, ИНН одинаков в источнике и в основной БД.
- ~~**Р-30. Импорт выгрузки генератора заменяет демо-набор целиком**~~ — заменено Р-52 (импорт — дельта). и сбрасывает загруженные данные и результаты
  прогонов (кроме параметров); во время прогона импорт запрещён (409). Выгрузка — полный снимок; если дописывать её
  поверх старой, в основных таблицах остались бы УПД прошлого набора. Импорт `events.csv` заменяет только
  ЕГРЮЛ/ЕФРСБ. Импорт — по относительному пути из каталога `smart-factoring.manual-upload.import-dir` (`MANUAL_UPLOAD_DIR`,
  по умолчанию `/data/manual-upload`) или ZIP-архивом. **Нужно подтверждение пользователя** (разрушительное действие).
- **Р-31. Блок 1 грузит справочники целиком** (менеджеры, клиенты, весь реестр покупателей с отчётностью и
  ЕГРЮЛ/ЕФРСБ), а документы и платежи — только клиентов прогона и не позже даты расчёта. Следующие блоки берут
  из основных таблиц УПД и платежи клиентов прогона с датой не позже даты расчёта, поэтому прогон «назад» (К-15)
  не видит документы, загруженные прогоном с более поздней датой.
- **Р-32. Отзыв предложений (п. 3.9) применяется в блоке 5**, вместе с публикацией очереди: всё изменение очереди —
  одной транзакцией в конце успешного прогона; остановленный прогон очередь не трогает.
- **Р-33. Уведомления и сигналы — результат прогона** (таблица `notification` с `run_id`): эмулятор CRM показывает их из
  последнего успешного прогона, повторный прогон не дублирует уведомления о той же просрочке.
- **Р-34. Сверка: несколько номеров УПД в назначении** — платёж идёт на все названные УПД по старшинству, излишек —
  по п. 2.4. Платёж может закрыть УПД, подписанный позже даты платежа (предоплата) — BRD это не запрещает.
- **Р-35. Два режима сервиса моделей в backend** (`smart-factoring.ml.mode`, `ML_MODE`): `http` — сервис
  smart-factoring-ml по контракту, `stub` — встроенная заглушка (ответы для контрольных случаев — из
  `stub_buyer_scores.csv` / `stub_upd_scores.csv`, иначе значения по умолчанию; «нет истории» — по истории из запроса).
  По умолчанию `stub`: стенд и тесты работают без Python и без моделей коллеги. После моделей — `ML_MODE=http`.
- **Р-36. История оплат для модели задержки** — УПД клиентов прогона на дату расчёта плюс УПД других клиентов из их
  последнего успешного прогона (если прогон по части клиентов): «нет истории оплат» — по всем клиентам банка (п. 4.5).
- **Р-37. Модель задержки применяется к открытым УПД категорий 1–4** у покупателей с PD (без стоп-фактора и с данными).
  Просроченные УПД (5–8) не оцениваются: факторинг по ним не предлагается, в карточке у них PD покупателя.
- **Р-38. В запрос модели задержки добавлено поле `number`** (номер УПД) — для журнала и заглушки.
- **Р-39. Срок финансирования — в целых днях**: ожидаемая задержка из модели округляется до целого дня
  (в примере BRD 40 + 6 = 46). Деньги — с копейками, округление половины вверх.
- **Р-40. Напоминание менеджеру (п. 5.3, пункт 5) — по датам расчёта**: предложение в очереди дольше
  `ranking.reminder_days` дней между датой расчёта создавшего его прогона и текущей. На демо видно при сдвиге даты.
- **Р-41. Границы уровней риска — включительно** (PD ≤ 1% → A, ≤ 3% → B, ≤ 8% → C): так пример BRD п. 5.1
  («уровень B, PD 3%») согласуется с границами Р-13. **Подтвердить**; итоговые границы даст модель PD.
- **Р-42. Отзыв по УПД, которого нет в прогоне** (дата расчёта сдвинута раньше его подписания) — причина
  `NO_LONGER_ELIGIBLE`. Причины отзыва: `UPD_PAID`, `UPD_OVERDUE`, `NO_LONGER_ELIGIBLE`.
- **Р-43. LLM: режимы `stub` / `gigachat` / `off`** (`LLM_MODE`, по умолчанию `stub` — пока нет ключа). `stub` — шаблонные
  тексты причин и черновика; `off` и сбой GigaChat — причины шаблоном, черновика нет (п. 5.3). Промпты —
  `classpath:llm/*.txt`, их заменят промпты коллеги. Ответы GigaChat кешируются по SHA-256 входа (Р-7).
  В LLM уходят только факты карточки, без персональных данных (НФР-10). Сертификат НУЦ Минцифры — в truststore стенда.
- **Р-44. Роли проверяет gateway** (решение пользователя 25.10.2026, развивает Р-8). Роли realm Keycloak из
  `realm_access.roles`: `operator` — импорт данных ручной загрузки (`/manual-upload/**`) и запуск прогона (`POST /runs`);
  `manager` — эмулятор CRM (`/managers/**`, `/clients/**`, `/offers/**`); смотреть прогоны и параметры
  (`GET /runs/**`, `/parameters`) — обе роли; прочие пути backend — любому вошедшему. Без нужной роли — 403.
  Backend роли не проверяет (доступен только через gateway). UI читает роли из access token и скрывает недоступное:
  без `manager` нет раздела CRM, без `operator` экран процесса только для просмотра, без обеих — «Нет доступа».
  В демо одному пользователю выдаются обе роли.
- **Р-45. Лимит загрузки файлов в backend — 200 МБ** (ZIP выгрузки, полный `events.csv`).
- **Р-46. Тексты LLM запрашиваются параллельно** (`LLM_PARALLELISM`, по умолчанию 8): на объёме демо ~290 предложений
  × 2 вызова; последовательно с GigaChat это 20–30 минут против 10 по НФР-1.1. **Риск**: у тарифа GIGACHAT_API_PERS
  ограничение на одновременные запросы — тогда нужен другой тариф или тексты по запросу при открытии карточки.
- **Р-47. Эвристики сервиса моделей** (до обученных моделей коллеги): PD — логистическая оценка по коэффициентам
  отчётности, задержка — по дисциплине покупателя и пары; коэффициенты подобраны вручную, помечены `stub: true`.
- **Р-48. LLM — только через backend** (решение пользователя 26.10.2026). Один `LlmClient` на весь контур: тексты
  карточек в прогоне и запросы сервиса моделей. smart-factoring-ml в GigaChat напрямую не ходит, а вызывает
  `POST /internal/rest/llm/chat/completions` backend — стандартный путь API (по решению пользователя): ml ходит
  в backend напрямую по сети стенда, снаружи endpoint доступен через gateway как `/api/backend/llm/**` с токеном. Ключ, токен OAuth и предел одновременных запросов (`LLM_PARALLELISM`) — общие, поэтому прогон
  и сервис моделей вместе не превышают лимит тарифа. Клиент GigaChat: токен кешируется и обновляется по 401;
  429, 5xx и сетевые сбои — до 3 попыток; прочие 4xx — сразу ошибка; при `LLM_MODE=gigachat` без ключа backend не стартует.
  Ответ, заменённый цензурой GigaChat (`finish_reason=blacklist`), в карточку не идёт — причины шаблоном, без черновика.
  Вызывающий сервис может задать модель полем `model` запроса; не задана или пустая — `GIGACHAT_MODEL` стенда
  (решение пользователя 27.10.2026). Тексты карточек — всегда на модели стенда.
- **Р-49. Сертификат НУЦ Минцифры — PEM-файлом** (`GIGACHAT_CA_CERT`), а не в truststore образа: клиент GigaChat
  доверяет сертификатам JDK и дополнительно этому файлу; остальной TLS backend не меняется, образ пересобирать не нужно.
- **Р-50. Сервис моделей на стенде** (решение пользователя 26.10.2026: обучение моделей — у коллеги, мы — сервис
  и деплой; стенд сразу на `ML_MODE=http`). Сервис `ml` без внешних портов, образ из CI smart-factoring-ml (ghcr,
  smoke-проверка health), раскатывается тем же deploy workflow. Модели загружаются при старте — сломанный модуль
  модели не даёт сервису стартовать. Backend переживает недоступность ml: версии моделей тоже запрашиваются с
  повторами, при отказе прогон завершается со статусом «с предупреждениями», УПД — «ошибка оценки», без предложений.
- **Р-51. Сбои LLM видны в прогоне.** Шаг 5 пишет в журнал итог по текстам карточек (`LLM_TEXTS`: от LLM, из кеша,
  шаблоном, без черновика) и `LLM_ERROR` с причиной по каждой карточке без черновика; при сбоях шаг и прогон —
  «с предупреждением», метрика `textsBySource`. «No such model» от GigaChat перечисляет доступные модели.
- **Р-52. Импорт — дельта, без обнуления** (решение пользователя 27.10.2026, заменяет Р-30). Выгрузка добавляет
  новые записи и обновляет существующие по естественным ключам; то, чего нет в файле, не удаляется; история
  прогонов и решения менеджеров сохраняются. Все файлы выгрузки, кроме `manifest.json`, необязательны; ссылки
  (менеджер, клиент, договор пары) проверяются по файлу и по уже загруженному.
  - **Неизменяемые поля** при том же ключе: у договора — покупатель; у УПД — покупатель и договор; у платежа — получатель,
    плательщик, сумма, дата. Изменились — **строка пропускается** (конфликт), остальное загружается; УПД по договору
    в конфликте тоже пропускается.
  - **Изменяемые**: сумма УПД (корректировка), дата и отсрочка договора, назначение платежа, справочники — обновляются,
    изменения документов — в отчёте. Изменилась сумма УПД, уже переданного в факторинг, — предупреждение.
  - **Возможные дубли** (разные ключи, то же содержание: платёж — получатель, плательщик, сумма, дата, назначение;
    УПД — клиент, покупатель, дата, сумма) **загружаются с предупреждением** — отличить дубль от двух реальных
    одинаковых платежей система не может.
  - Ошибки формата и ссылок по-прежнему отклоняют выгрузку целиком.
