# SMF-33. Сквозная проверка стенда test

Стенд: UI — http://188.127.254.192:8070, Swagger — http://188.127.254.192:8090/swagger-ui.html.
Наборы для импорта — `manual-upload/fixture-v1.zip` (контрольные случаи К-1…К-18, 6 клиентов) и
`manual-upload/perf-volume.zip` (объём демо: 100 клиентов, 300 покупателей, 1 500 открытых УПД) в корне репозитория,
в git не входят. Собрать: `python -I docs/claude/tools/build_manual_upload_zips.py`.

Что проверяется на стенде, а что — автотестами:

- **Автотесты** (`mvn verify`, 101 тест) проверяют числа К-1…К-18 до рубля — на заглушке моделей с оценками из
  `stub_*_scores.csv` фикстуры. На стенде `ML_MODE=http`: PD и задержку считают эвристики сервиса ml, поэтому уровни
  риска, суммы и доход **отличаются от CASES.md** — это ожидаемо.
- **Стенд** проверяет, что всё собрано вместе: вход и роли, gateway → backend → ml, GigaChat, импорт, прогон,
  экран процесса, CRM. И случаи, не зависящие от моделей (шаг 5).

## 0. Подготовка

1. GitHub → smart-factoring-deploy → Settings → Environments → `test`:
   `LLM_MODE=gigachat`, секрет `GIGACHAT_AUTH_KEY`, `LLM_PARALLELISM=1` (Freemium — 1 поток), при желании `GIGACHAT_MODEL`.
   `ML_MODE` не задавать (по умолчанию `http`).
2. Переменные окружения попадают на стенд **только при деплое**. Если их меняли после последнего деплоя —
   Actions → Deploy → Run workflow: `test`, сервис `все`, тег `test`. Job зелёный = все 4 контейнера прошли healthcheck.
3. На VDS (по желанию): `docker compose ps` в `VDS_DIR` — `backend`, `gateway`, `ui`, `ml` в состоянии `healthy`;
   `grep -E "LLM_MODE|ML_|GIGACHAT_MODEL|LLM_PARALLELISM" .env`.

## 1. Вход и роли

1. UI → войти тестовым пользователем (после выдачи ролей — заново).
2. **Ожидается**: в шапке оба раздела — «Экран процесса» и «Эмулятор CRM»; на экране процесса есть «Запуск прогона»
   и «Импорт данных ручной загрузки». Если раздела нет — в токене нет роли: выйти и войти снова.

## 2. GigaChat через backend

Swagger → Authorize → `POST /api/backend/llm/chat/completions`:

```json
{ "messages": [ { "role": "user", "content": "Что такое факторинг? Одним предложением." } ], "maxTokens": 200 }
```

**Ожидается** `200`, `content` — ответ, `model` — например `GigaChat:2.0.28.2`.
`503 LLM_DISABLED` — на стенде не `LLM_MODE=gigachat` (шаг 0.2); `503 LLM_UNAVAILABLE` — смотреть `message`
(TLS: не доехал `certs/`; 401: ключ; 429: параллельность больше тарифа).

## 3. Импорт фикстуры

Вкладка «История прогонов» → «Загрузка данных» → `fixture-v1.zip`. Импорт — дельта (Р-52): ничего не стирает, в ответ —
отчёт по таблицам и замечания. Начать с нуля — «Очистка данных» на той же вкладке (с подтверждением).
Повторный импорт того же архива — всё «без изменений», прогоны и решения на месте.
**Ожидается**: дата данных 2026-10-24; 8 клиентов, 9 покупателей в реестре, 39 УПД, 13 оплат; события ЕФРСБ загружены.

## 4. Прогон

«Запуск прогона», дата расчёта 2026-10-24, все клиенты.

**Ожидается**:
- статус «выполнен» (или «с предупреждениями» — смотреть журнал), 5 шагов с числами;
- в версиях моделей: `pd = pd-heuristic-1`, `delay = delay-heuristic-1` (ответил сервис ml; `pd-stub-1` — backend
  на заглушке, `unavailable` — ml недоступен), `llm = gigachat:GigaChat-2:v1`;
- шаг 1: 6 клиентов (C7 — уже клиент факторинга, C8 — без согласия ЭДО не загружены), 37 УПД, 1 покупатель без данных;
- воронка: 37 → 28 открытых → … → предложения;
- время: секунды на шагах 1–4; шаг 5 дольше — тексты GigaChat идут по одному (`LLM_PARALLELISM=1`), ~2 запроса
  на предложение.

## 6. Карточка предложения и CRM

1. Эмулятор CRM → менеджер → очередь предложений.
2. Открыть предложение: причины оценки и черновик сообщения — **текст GigaChat** (не шаблон «Добрый день! По отгрузке
   покупателю … банк готов сразу выплатить …»). Шаблон без черновика — GigaChat не ответил, причина в журнале прогона.
3. Карточка клиента: дебиторка, просрочено, доступно к финансированию.
4. «Передать в факторинг» по одному предложению, «Отклонить» по другому.
5. Новый прогон на ту же дату. **Ожидается** (К-16): обоих нет в очереди, дублей нет; тексты карточек — из кеша
   (шаг 5 быстрее, к GigaChat не обращается).

## 7. Дата расчёта (К-15)

Прогон на 2026-11-25: часть УПД просрочена, их предложения отозваны (уведомления в CRM).
Прогон на 2026-10-21: оплата P-0006 не учитывается, U-1103 снова открыт.

## 8. Объём демо (НФР-1.1, ≤ 10 минут)

«Очистка данных» (импорт — дельта и лёг бы поверх фикстуры), затем импорт `perf-volume.zip`, прогон. Предложений ~270 → ~540 запросов к GigaChat; при `LLM_PARALLELISM=1` это
**десятки минут** — НФР не выполнится на Freemium (Р-46). Чтобы проверить время самой системы — на время этого
прогона `LLM_MODE=stub` (деплой), ожидается ~3–5 с; с GigaChat — замерить и записать, это вход для решения по тарифу.
