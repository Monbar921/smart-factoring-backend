# SMF-33. Конспект требований

Источники: `docs/Smart_Factoring_BRD_v2.1.docx` (BRD 2.1, 24.10.2026), `docs/Smart_Factoring_C4_Architecture_v0.2.pdf` (C4 0.2).

## Суть

По запросу оператора система делает **прогон** (блоки 1–5) по клиентам банка (поставщикам): загружает УПД и платежи,
сверяет оплаты, категоризирует дебиторку, оценивает покупателей (PD + задержка), считает экономику факторинга по УПД,
ранжирует и выдаёт менеджерам очередь предложений. **Блок 6** (передать в факторинг / отклонить) — после прогона, по
действию менеджера. Всё внешнее — имитации, покупатели реальные (открытые данные), клиенты/УПД/платежи — синтетика.

## Ключевые правила (чек-лист для реализации)

**Прогон (ПР):** один за раз (ПР-3); параметры — набор клиентов, дата расчёта (по умолч. последняя дата данных);
статусы прогона `RUNNING / DONE / DONE_WITH_WARNINGS / STOPPED`; статусы шага `ожидает/выполняется/готово/предупреждение/остановлен`;
результат каждого шага сохраняется (ПР-5); срез по дате расчёта (ПР-9); повторный прогон обновляет, не дублирует (ПР-8);
статусы предложения `в очереди / передано в факторинг / отклонено / отозвано`.

**Блок 1:** загрузка УПД+договоров, платежей, внешних данных покупателя (с датой данных). Нет записи по ИНН → «нет данных по покупателю».

**Блок 2 (сверка):** по номеру УПД → по номеру договора FIFO → по покупателю FIFO; переплата переносится
(договор → покупатель); нераспределённый остаток не участвует.

**Блок 3 (категории 1–8):** плановая дата = отгрузка + отсрочка; дни до срока = план − дата расчёта (0 — ещё не наступил).
1/2 — неоплачен, ≤30 / >30 до срока; 3/4 — частично, ≤30 / >30; 5/6 — частично, просрочка >30 / ≤30; 7/8 — неоплачен, >30 / ≤30.
Предложение живёт только в кат. 1–4, иначе «отозвано». Кат. 5–8: уведомление менеджеру; 5,7 — сигнал в риск. История платежей покупателя.

**Блок 4 (скоринг):** стоп-факторы (банкротство/ликвидация/исключение) → PD один раз на покупателя (сетевой эффект),
базовый PD «мало данных» (нет отчётности за год / выручка < 120 млн / моложе года) → модель задержки по УПД
(P(задержка > 14 дн), P(просрочка 90+), ожидаемые дни) → уровень A–D → 3 причины. Пять ситуаций отсутствия данных (п. 4.5).

**Блок 5 (решение):** порядок из 6 шагов (п. 5 вводная); экономика — простые проценты /365 (п. 5.1, пример на цифрах);
правила сверху вниз, одна причина (п. 5.2); ранг = TR × доход (до лимита); топ-3 на клиента; затем деление остатка лимита
покупателя между всеми клиентами по убыванию ранга (тай-брейк: дата УПД, номер), пересчёт цены/дохода пропорционально;
карточка, LLM-причины и черновик (без LLM — без черновика); уведомление если сумма > 1 млн; напоминание через 3 дня.

**Блок 6:** решение сразу пишется, пакет в имитацию ВТБ Факторинга; переданные УПД уменьшают остаток лимита, пока не оплачены.

**НФР:** прогон ≤ 10 мин на 100 клиентов / 1 500 УПД; модель ≤ 1 с на УПД, параллельно; карточка ≤ 2 с; экран обновляется ≤ 5 с;
повтор обработки УПД 2 раза; идемпотентная загрузка (номер, дата, ИНН клиента); детерминизм (НФР-5); версия модели + дата данных
в каждом результате (НФР-6); аудит-журнал (НФР-7).

**Контрольные случаи:** К-1…К-18 (Приложение Б) — это и есть наш приёмочный набор.

## Параметры (Приложение А) — выносим в конфиг/таблицу параметров

(ликвидность < 0,2; отсрочка ≥ 60); топ-3; напоминание 3 дня; уведомление > 1 млн; повторы 2; ручная проработка 200 мин.
