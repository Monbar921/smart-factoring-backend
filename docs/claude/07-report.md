### Backend

- **Импорт данных ручной загрузки** (`POST /manual-upload`): папка выгрузки генератора на сервере или ZIP, `events.csv` отдельно;
  проверка формата с перечнем ошибок; формат — [module-0/manual-upload-format.md](module-0/manual-upload-format.md).
- **Прогон** (`POST /runs`): один за раз, дата расчёта и набор клиентов, статусы прогона и шагов, журнал, история,
  восстановление после перезапуска; блоки 1–5 строго по BRD, результаты каждого шага хранятся по прогону.
- **Блок 5** сверен с BRD: оба примера экономики п. 5.1 и пример деления лимита п. 5.3 — до рубля.
- **Блок 6 и CRM**: очередь, карточка клиента (с кассовым разрывом), уведомления, «Передать в факторинг» (пакет
  в имитацию ВТБ Факторинга) и «Отклонить».
- **Детализация**: воронка УПД, список УПД с фильтрами, путь УПД по шагам, покупатели и клиенты прогона.
- **Модели**: `ML_MODE=stub` (по умолчанию) или `http` — сервис smart-factoring-ml. **LLM**: `LLM_MODE=stub|gigachat|off`.

### Что не проверено

- **UI вживую в браузере**: нужен работающий стенд с Keycloak; проверено тестами с подменой API и сборкой.
- **GigaChat**: нет ключа; клиент написан по документации API, не вызывался.
- **Время прогона с реальным GigaChat**: при последовательных вызовах было бы 20–30 мин; сделал 8 параллельных (Р-46).
- **Генератор коллеги**: формат выгрузки согласован только с моей фикстурой.
