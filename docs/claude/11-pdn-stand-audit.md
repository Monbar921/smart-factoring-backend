# SMF-33. Персональные данные на стенде: проверка 22.11.2026

Что из персональных данных реально есть на стенде хакатона (test/prod на VDS) и что нужно сделать, чтобы хранение
соответствовало 152-ФЗ. Проверка — по коду и конфигурации всех репозиториев и по наборам загрузки; сам стенд (база,
Keycloak, логи) не открывался — команды для сверки на сервере ниже. Общая картина данных и мер —
[docs/security.md](../security.md); здесь — только стенд.

## Итог

Данных клиентов-физлиц на стенде нет, вывод `security.md` («в демо персональных данных нет») для **бизнес-данных**
подтверждён. Но стенд — публичный сайт с учётными записями, поэтому персональные данные на нём есть: **данные
пользователей стенда и IP-адреса посетителей**. Второе в `security.md` не было учтено — исправлено в этом же изменении.

## Что проверено и что найдено

| `batch_01…05.zip`, `delivery.zip` (генератор коллеги, `gen-1.0`, RFSD) | по 100 клиентов, 297 покупателей, ~22 000 УПД и ~24 000 оплат на партию | клиенты — «Клиент 0001», ИНН 10-значные; покупатели — реальные ИНН юрлиц из RFSD, названия пустые; назначения платежей — шаблоны («Оплата по УПД № …»); ФИО, «ИП», почт, телефонов не найдено |

Поиск: 12-значные ИНН (физлица и ИП), ФИО полностью и с инициалами, «ИП / КФХ / Глава», почта, телефон — по всем
CSV. Схема БД (все таблицы Liquibase): поля, которые могли бы содержать персональные данные, — только `manager.full_name`
(«Демо-менеджер») и логины пользователей (ниже). Свободный текст — `payment.purpose`, `run_log.message`,
`offer.reasons_text`/`message_draft` (тексты LLM по фактам карточки, без ФИО).

Оговорка: ИНН покупателей реальные — это открытые сведения о юрлицах, не персональные данные. Если генератор
когда-нибудь возьмёт из RFSD ИП (12-значный ИНН), это станут персональные данные — проверка выше повторяется на
каждой новой выгрузке (критерий — нет 12-значных ИНН).

### Данные пользователей стенда — персональные данные есть

| Данные | Где | Чьи | Сколько хранится |
|---|---|---|---|
| Логин, почта, имя и фамилия, хеш пароля, секрет OTP | база `keycloak` (тот же Postgres) | команда, тестовый пользователь (`tester@smart-factoring.test`), гость `demo` («Гость Демо») | до удаления пользователя |
| Логин в журнале | `run.initiator`, `run_attempt.initiator`, `offer.decided_by` | кто запускал анализ и решал по предложениям | до «Очистить данные» |
| Логин в логах backend | «Прогон N запущен: login», отказы в доступе | то же | ротация 5×10 МБ |
| Соответствие «пользователь → менеджер» | атрибут `manager_code` пользователя в базе `keycloak` (Р-90; раньше — переменная GitHub `MANAGER_LOGINS`) | менеджеры команды | до удаления пользователя |

Раньше соответствие лежало в переменной GitHub `MANAGER_LOGINS` с логинами (`anna:M1`) — если логины были фамилиями
или именами, это персональные данные, переданные в GitHub (США). После Р-90 переменную нужно удалить в GitHub.

### IP-адреса посетителей — не было в `security.md`

| Где | Что пишется | Основание в коде |
|---|---|---|
| лог gateway (`reactor.netty.http.server.AccessLog`) | на **каждый запрос**: `ip=` адрес соединения и `xff=` X-Forwarded-For, метод, путь с параметрами, статус, время. Через Caddy и nginx UI реальный IP посетителя — в `xff` (nginx ставит `$proxy_add_x_forwarded_for`); при обращении напрямую к `:8090` — в `ip` | `AccessLogConfiguration` (gateway) |
| лог Keycloak | неудачный вход: `LOGIN_ERROR … ipAddress=…, username=…` — введённый логин, иногда это ошибочно введённый пароль | слушатель событий `jboss-logging` по умолчанию (WARN); на стенде не сверено |
| база `keycloak` | защита от подбора: последний IP неудачного входа по пользователю | `bruteForceProtected: true` в realm |
| nginx UI, Caddy | access-лог не ведётся (`access_log off`, в Caddyfile нет `log`) | конфигурация |

IP-адрес вместе со временем и действиями — персональные данные (позиция Роскомнадзора; на стенд заходят эксперты
конкурса через «Запуск демо»). Хранение — логи Docker на VDS, ротация 5 файлов по 10 МБ на сервис.

## Что нужно соблюсти (152-ФЗ) и статус

Стенд — отдельная от пилота обработка: оператор здесь не банк, а команда (владелец стенда), субъекты — участники
команды и посетители демо. Требования ниже — для этого контура; пилот описан в `security.md`.

| № | Требование | Что сделать на стенде | Статус |
|---|---|---|---|
| 1 | Минимизация (ч. 5 ст. 5) | IP посетителя в логе gateway не нужен для разбора сбоев — **маскировать последний октет** (`203.0.113.x`) или убрать `xff`; путь с параметрами оставить (персональных данных в параметрах нет) | **открыт** — правка `AccessLogConfiguration`, команда gateway |
| 2 | Локализация (ч. 5 ст. 18): запись и хранение ПДн граждан РФ — в базах в РФ | VDS SmartApe — проверить по договору хостинга, что дата-центр в РФ; `MANAGER_LOGINS` после Р-90 не нужна — удалить переменную в GitHub | **открыт** — владелец стенда |

## Сверка на стенде (владелец стенда, на VDS)

```bash
# пользователи realm: нет ли реальных почт и лишних учётных записей
docker compose -f infra/docker-compose.yml exec keycloak /opt/keycloak/bin/kcadm.sh get users -r <realm> \
  --fields username,email,firstName,lastName,enabled   # после kcadm config credentials
# что пишет gateway и Keycloak об IP
docker compose logs --tail 20 gateway | grep -E 'xff=[0-9]'
docker compose -f infra/docker-compose.yml logs keycloak | grep -c LOGIN_ERROR
# логины в журнале
psql ... -c "select distinct initiator from smart_factoring_test.run union select distinct decided_by from smart_factoring_test.offer"
# 12-значные ИНН в загруженных данных (должно быть 0)
psql ... -c "select count(*) from smart_factoring_test.client where length(inn)=12"
```

Удалить `MANAGER_LOGINS` (больше не используется, Р-90): GitHub → smart-factoring-deploy → Settings → Environments →
`test`/`prod` → Variables.
