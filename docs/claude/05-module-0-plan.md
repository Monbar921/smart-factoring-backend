Цель: зафиксировать данные и интерфейсы до того, как писать логику. После модуля 0 параллельно могут идти
backend (модули 1–9), UI (11–12) и коллега (модели и генератор): у всех один контракт.

## 0.1 Модель данных

Деньги — `numeric(19,2)`, вероятности и ставки — `numeric(9,6)`, даты — `date`, моменты — `timestamptz`,
ключи — `bigint generated always as identity`. Перечисления — `varchar` + `check` (без отдельных справочников, их мало).

### Таблицы `demo_*` — имитации источников и получателей (ДД-1)

| Таблица | Что | Ключ идемпотентности |
|---|---|---|
| `demo_manager` | менеджеры (в демо 1) | `code` |
| `demo_client` | клиенты: ИНН, название, отрасль, регион, абс. ликвидность, менеджер, согласие на ЭДО, клиент факторинга | `inn` |
| `demo_buyer` | реестр покупателей: ИНН, название, ОКВЭД, регион, дата регистрации | `inn` |
| `demo_buyer_financials` | отчётность ГИР БО по годам (строки баланса и ОФР, нужные для PD) | `inn, year` |
| `demo_efrsb_event` | сырые строки `events.csv` (ЕГРЮЛ-статус, дело, события) | `inn, message_number` |
| `demo_contract` | договоры: клиент, покупатель, номер, дата, отсрочка, дней | `client_inn, number` |
| `demo_upd` | УПД: номер, дата отгрузки = дата подписания, сумма, договор | `number, date, client_inn` (НФР-3) |

| `demo_factoring_package` | имитация ВТБ Факторинга: принятые пакеты (jsonb) | `offer_id` |
| `demo_risk_signal` | имитация риск-подразделения: сигналы о проблемном покупателе | `run_id, buyer_inn` |

### Основные таблицы — загруженные данные (блок 1)

| Таблица | Что |
|---|---|
| `manager`, `client`, `buyer` | копии справочников из источника + `loaded_at` |
| `buyer_external_data` | по ИНН: статус ЕГРЮЛ + дата, стадия дела о банкротстве + даты, отчётность (jsonb по годам), **дата данных** (п. 1.3) |
| `contract`, `upd`, `payment` | загруженные документы; уникальность как в источнике — повторная загрузка не создаёт дублей |

### Основные таблицы — прогон

| Таблица | Что | Требования |
|---|---|---|
| `run` | статус, дата расчёта, набор клиентов (jsonb), кто запустил (оператор/API), начало/конец, снимок параметров (jsonb), версии моделей, дата данных, итоговые числа | ПР-2, ПР-6, ЭП-8, НФР-6, НФР-7 |
| `run_step` | `run_id, step_no 1..5`, статус, начало, длительность, числа шага (jsonb) | ПР-5, ЭП-2, ЭП-3 |
| `run_log` | журнал: время, уровень, шаг, УПД/покупатель, сообщение, детали | ЭП-6, НФР-7 |
| `payment_allocation` | `run_id, payment_id, upd_id, amount, rule (2.1/2.2/2.3/2.4)`; нераспределённый остаток — строка с `upd_id = null` | блок 2, К-5, К-6 |
| `upd_state` | `run_id, upd_id`: плановая дата, дней до срока, остаток, оплачен полностью, категория 1–8, дата фактической оплаты, дней задержки | блок 3, 3.11 |
| `buyer_score` | `run_id, buyer_inn`: стоп-фактор + причина, нет данных, нет истории оплат, PD, источник PD (модель/базовый), «мало данных», уровень A–D, 3 причины (jsonb), версия модели, дата данных | блок 4 |
| `buyer_pd_cache` | `buyer_inn, data_date, model_version` → PD и причины: PD не пересчитывается без новых данных | п. 4.2 |
| `upd_score` | `run_id, upd_id`: статус (оценён / нет истории / ошибка), P(задержка > порога), P(90+), ожидаемые дни, «нет истории пары», версия модели | п. 4.3–4.5 |
| `upd_decision` | `run_id, upd_id`: решение, причина (код), доля аванса, срок, EAD до/после лимита, EL, фондирование, опер., маржа, цена ₽ и %, доход до/после, TR, ранг, место в топ-3, пометки | блок 5, НФР-7 |
| `offer` | **живёт между прогонами**: `upd_id` (уникален среди не закрытых), статус (в очереди / передано / отклонено / отозвано), текущие условия, первый и последний прогон, «новое в прогоне», дата постановки в очередь, решение (кто, когда) | ПР-8, 3.9, блок 6, Р-16 |
| `notification` | `run_id`, менеджер, тип (новое предложение / просрочка / напоминание / сигнал в риск), УПД, данные | 3.10, 5.3 п.5, 5.4 |
| `llm_text_cache` | хеш входа → тексты причин и черновик, провайдер | Р-7 |
| `parameter` | код, значение, тип, раздел, описание; дефолты — Приложение А | Р-9 |

Почему результаты по прогонам, а не «последнее состояние»: детализация и путь УПД (ЭП-5), история прогонов (ЭП-8)
и аудит (НФР-6, НФР-7) требуют видеть, что было в конкретном прогоне. Объём — около 1 500 строк на таблицу за прогон.

«Один прогон за раз» — частичный уникальный индекс `run (status) where status = 'RUNNING'` (Р-5).
Воронка (ЭП-4) — представление (`005-views.xml`) поверх `upd_state` + `buyer_score` + `upd_decision`.

## 0.4 Контракт сервиса моделей

- `GET /v1/health`, `GET /v1/models` — версии моделей.
- `POST /v1/pd/score` — пачка покупателей → по каждому: PD, источник (модель/базовый), «мало данных», 3 причины
  (признак, направление, вклад), версия модели.
- `POST /v1/delay/score` — пачка УПД + порог задержки (7/14/30) → по каждому: статус (оценён / нет истории оплат),
  P(задержка > порога), P(90+), ожидаемые дни, «нет истории пары», версия модели.

**Ключевое решение — что передаёт backend (Р-22, на согласование):** сырые данные, а не готовые признаки.
Для PD — отчётность по годам и профиль, для задержки — УПД, договор и история оплат покупателя по всем клиентам на дату расчёта.
Признаки считает сервис моделей тем же кодом, что использовался при обучении у коллеги. Так обучение и
работа сервиса не разойдутся, а backend не дублирует feature engineering. Цена — запрос тяжелее, но на 1 500 УПД
это единицы мегабайт.

Заглушка (модуль 5) отвечает детерминированно по хешу ИНН/УПД, с «правильными» ответами для контрольных случаев.

## 0.5 Формат демо-данных

- **Выгрузка генератора:** папка с CSV (UTF-8, `;`, заголовок) + `manifest.json` (версия формата, seed, дата данных, дата снимка):
  `managers.csv`, `clients.csv`, `buyers.csv`, `buyer_financials.csv`, `contracts.csv`, `upds.csv`, `payments.csv`.
  Колонки — по таблицам `demo_*` выше. Необязательная колонка `control_case` (К-1…К-18) в клиентах/УПД/платежах —
  для приёмочных тестов.
- **`events.csv`:** `;`, UTF-8, кавычки. Импорт как есть в `demo_efrsb_event`. Стоп-фактор считается на дату снимка
  по статусу ЕГРЮЛ (ликвидация, исключение, банкротство) и стадии дела (наблюдение, конкурсное производство и др.,
  без даты окончания). Точный список значений составлю по фактическим уникальным значениям файла.
- **Ручная фикстура:** до выгрузки коллеги — маленький набор в `app/src/test/resources/demo/` в том же формате,
  с контрольными случаями. Это и тесты, и пример формата для коллеги.
