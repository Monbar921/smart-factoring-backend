# SMF-33. Контракт с LLM (GigaChat): что уходит в промпт и какой ответ ждём

Для коллеги, который делает промпты и тексты LLM. Описано так, как сейчас работает backend
(`feature/factoring-service/.../llm/`); промпты — в `src/main/resources/llm/`, их можно заменить своими.

## Когда и зачем вызывается LLM

Шаг 5 прогона («Решение и предложение»), только для УПД, по которым сформировано предложение. На каждое предложение —
**два независимых запроса** к GigaChat `POST /chat/completions`:

| Запрос | Системный промпт | Куда идёт ответ | Кто читает |
|---|---|---|---|
| причины оценки | `llm/reasons-prompt.txt` | `offer.reasons_text` | менеджер в карточке предложения (CRM) |
| черновик сообщения клиенту | `llm/draft-prompt.txt` | `offer.message_draft` | менеджер копирует и отправляет клиенту |

Ответ используется **как есть** (только обрезаются пробелы по краям): без разбора, без JSON.

## Запрос

```json
{
  "model": "GigaChat-2",
  "messages": [
    { "role": "system", "content": "<текст reasons-prompt.txt или draft-prompt.txt>" },
    { "role": "user", "content": "<факты предложения, формат ниже>" }
  ],
  "temperature": 0.2,
  "max_tokens": 512
}
```

- Модель — из настройки `GIGACHAT_MODEL` стенда, одна на оба запроса (тексты карточек). Для своих запросов
  через backend модель можно задать полем `model` (см. последний раздел).
- `temperature` 0,2 и `max_tokens` 512 — константы в `ExplainerService`.
- Сообщений всегда два: системное (промпт целиком из файла) и пользовательское (факты). Истории диалога нет.

## Пользовательское сообщение: факты предложения

Одинаковое для обоих запросов. Только то, что менеджер и так видит в карточке; персональных данных нет (НФР-10).
Формат — текст, строки фиксированные:

```
Клиент: <название клиента>
Покупатель: <название покупателя>, ИНН <ИНН>
УПД: № <номер> от <ГГГГ-ММ-ДД>
Уровень риска покупателя: <A|B|C>, PD <x,x%>[ (мало данных: базовый PD по отрасли и размеру)]
Сумма финансирования: <сумма> руб.[ (уменьшена до остатка лимита на покупателя)]
Цена: <сумма> руб., <x,x%> годовых, срок <N> дн.[; вероятна задержка оплаты, аванс на ступень ниже]
Главные причины оценки покупателя:
- <название причины>[ = <значение>]: <повышает риск|снижает риск>
- ...
```

- В квадратных скобках — части, которые есть только при соответствующем признаке.
- Суммы — целые рубли с разделителем тысяч; проценты — до двух знаков, запятая (`0,5%`, `20,7%`).
- **Причины** (до трёх) — из ответа сервиса моделей (`reasons[]`: `title`, `value`, `direction`). `title` попадает
  в промпт дословно, поэтому названия причин в твоих моделях должны быть человеческими русскими фразами
  («Доля собственного капитала», а не `equity_ratio`). Уровня D в фактах не бывает: по D предложения нет.

### Пример (УПД U-1004 фикстуры, контрольный случай К-1)

Значения причин — иллюстрация в формате эвристик сервиса моделей:

```
Клиент: ООО "Альфа-Трейд"
Покупатель: ООО "БРИГ", ИНН 0277120989
УПД: № U-1004 от 2026-10-01
Уровень риска покупателя: A, PD 0,5%
Сумма финансирования: 4 500 000 руб.
Цена: 102 082 руб., 20,7% годовых, срок 40 дн.
Главные причины оценки покупателя:
- Доля собственного капитала = 0.4196: снижает риск
- Маржа чистой прибыли = 0.0582: снижает риск
- Текущая ликвидность = 1.5714: снижает риск
```

## Какой ответ ждём

Обычный текст, **без markdown, списков, приветствия и подписи** — он вставляется в карточку и в черновик письма как есть.

| | Причины оценки | Черновик сообщения клиенту |
|---|---|---|
| Для кого | менеджер банка | клиент (компания-поставщик) |
| Объём | 2–4 предложения | 3–5 предложений |
| Тон | простой, объясняющий | деловой, дружелюбный, на «вы» |
| Обязательно | почему покупатель оценён так (по причинам из фактов) | покупатель, номер УПД, сумма к выплате сразу, срок, стоимость в рублях и % годовых |
| Нельзя | выдумывать цифры; слова «модель», «SHAP», «логит», «PD» (говорить «вероятность дефолта») | упоминать оценку риска, вероятности и причины — внутренняя информация банка |

Пример черновика (как выглядит шаблон, когда LLM выключена):

> Добрый день! По отгрузке покупателю ООО "БРИГ" (УПД № U-1004 от 2026-10-01) банк готов сразу выплатить 4 500 000 руб.,
> не дожидаясь оплаты от покупателя. Срок - 40 дн., стоимость - 102 082 руб. (20,7% годовых). Если интересно, оформим
> факторинг в ВТБ Факторинге: от вас нужно только согласие.

## Что backend делает с ответом

- **Кеш.** Ответы кешируются по хешу «модель + версия промптов + факты»: повторный прогон с теми же фактами
  к GigaChat не ходит и даёт те же тексты. Сменил промпты — подними `PROMPT_VERSION` в `ExplainerService` (сейчас `v4`),
  иначе останутся старые тексты из кеша.
- **Сбой** (GigaChat недоступен, ошибка, ответ заменён цензурой — `finish_reason = blacklist`): причины — шаблоном
  по тем же фактам, черновика нет. Предложение всё равно уходит менеджеру; в журнале прогона — `LLM_ERROR` с причиной.
- **Ответ не проверяется** на длину и содержание — ограничения держит промпт.
- `LLM_MODE=stub` (по умолчанию на стенде без ключа) — оба текста шаблонные, к GigaChat запросов нет.

## Как подключить свои промпты

1. Заменить текст в `feature/factoring-service/src/main/resources/llm/reasons-prompt.txt` и `draft-prompt.txt`
   (UTF-8, весь файл — системное сообщение).
2. Поднять `PROMPT_VERSION` в `ExplainerService`.
3. Если нужны другие факты (новые поля, другой порядок) или другие `temperature` / `max_tokens` — это правка
   `ExplanationFacts.describe()` / `ExplainerService`, скажи, что нужно.

## LLM для твоих моделей

Если моделям в сервисе моделей нужна LLM, она доступна только через backend (ключ и лимит тарифа — общие):
`POST http://backend:8080/internal/rest/llm/chat/completions` с `{ "messages": [...], "temperature", "maxTokens", "model" }`
(`model` необязательна: не задана — модель стенда `GIGACHAT_MODEL`; доступные — `GET /internal/rest/llm/models`),
ответ `{ "content", "model", "finishReason", "promptTokens", "completionTokens" }`. В smart-factoring-ml готов клиент
`service/app/llm.py`; подробнее — раздел «LLM для сервиса моделей» в [module-0/backend-api.md](module-0/backend-api.md).
