# Данные, безопасность и комплаенс

Как Smart Factoring обращается с данными клиентов банка: что обрабатывается, кто что видит, что уходит наружу и что
нужно для пилота в контуре ВТБ. Документ описывает систему как она есть; что появится только на пилоте, помечено.
Решения с номерами Р-N — [claude/02-decisions.md](claude/02-decisions.md).

Логика документа — «цель → граница → проверка» (воркшоп «Защита данных: от требований закона к техническим решениям»,
20.11.2026): у каждой меры есть проверка и её результат; то, что не проверено, так и помечено — с владельцем и условием.

## Условие допуска реальных данных

Пока чек-лист не закрыт, система работает **только на синтетике и открытых данных** — демо, стенды хакатона. Реальные
данные клиентов банка допускаются после закрытия всех пунктов, кроме помеченных «на пилоте» с владельцем-банком.
Чек-лист — шесть вопросов воркшопа перед первым пилотом, заполнен по нашему проекту на 21.11.2026.

| Вопрос | Ответ по проекту | Статус | Владелец, срок |
|---|---|---|---|
| **Данные**: какие данные и чьи, есть ли персональные? | Перечень и классы — [«Какие данные»](#какие-данные-обрабатываются); персональные — клиенты-ИП, подписанты УПД, работники банка; поля с целью — [«Цель каждого поля»](#цель-каждого-поля-и-минимизация) | закрыт для MVP; на пилоте — сверить с выгрузками банка | команда; на пилоте — банк |
| **Основание**: на каком основании обрабатываем? | Банк — оператор, мы — по поручению; основание по каждой категории — [«Роли и основания»](#роли-сторон-и-правовые-основания); согласие на анализ ЭДО — отдельный документ банка | открыт: договор поручения и текст согласия готовит банк | банк, до пилота |
| **Маршруты**: куда данные уходят, кто получатель? | [Карта обработки](#карта-обработки-данных), [внешние получатели](#внешние-получатели): за пределы контура — только GigaChat с маскированием (по решению банка), трансграничной передачи персональных данных нет | закрыт для MVP | команда |
| **Права**: кто видит какие данные? | Роли и закрепление клиентов за менеджером на всех экранах (Р-75, Р-79), LLM пользователю закрыта (Р-80), OTP для оператора, руководителя и администратора — [«Кто что видит»](#кто-что-видит) | закрыт в коде; на стенде — после выката и `security-setup.sh` | владелец стенда, до 29.11.2026 |
| **Завершение**: что происходит с данными и доступами после пилота? | [Удаление](#жизненный-цикл-данных-и-удаление) — перечень копий и способ удаления; [реестр доступов](#реестр-доступов-и-их-отзыв) — срок и отзыв | закрыт для стенда; на пилоте — сроки хранения банка | владелец стенда; на пилоте — банк |
| **Проверка**: чем подтверждено? | [Свидетельства](#модель-угроз-и-свидетельства-проверок): тесты, сканеры в CI, ручные проверки с датой | частично: проверки на стенде не проведены (HTTPS, OTP, ZAP по стенду) | владелец стенда, до 29.11.2026 |

## Какие данные обрабатываются

| Данные | Откуда в MVP | Откуда на пилоте | Класс |
|---|---|---|---|
| Покупатели: ИНН, ОГРН, наименование, ОКВЭД, регион, отчётность | открытые данные: ГИР БО (RFSD), ЕГРЮЛ, ЕФРСБ | те же + сервис проверки контрагентов банка | открытые сведения о юрлицах |
| Клиенты (поставщики): ИНН, наименование, отрасль, ликвидность, менеджер | синтетика | хранилище банка, CRM | банковская тайна (ст. 26 Закона «О банках и банковской деятельности»); у клиента-ИП ИНН и ФИО — персональные данные |
| УПД, договоры, платежи клиента по покупателям | синтетика | ЭДО (с согласия клиента), выписки | банковская и коммерческая тайна |
| Оценки: PD, задержка, уровень риска, предложение, решение менеджера | расчёт системы | расчёт системы | внутренняя информация банка |
| Пользователи: логин, почта, роли, время входа | Keycloak стенда | IAM банка | персональные данные работников |
| IP-адреса посетителей | лог gateway (`xff=`, `ip=`) на каждый запрос — маскированные, без последнего октета; Keycloak — полностью, при неудачном входе | то же, в SIEM банка | персональные данные посетителей |

В демо персональных данных клиентов нет (НФР-10): покупатели — юрлица из открытых источников, клиенты, УПД и платежи
синтетические (проверено по всем наборам загрузки — [claude/11-pdn-stand-audit.md](claude/11-pdn-stand-audit.md)).
Персональные данные на стенде — только пользователей (учётные записи, логины в журнале) и IP-адреса посетителей в
логах; что для них нужно сделать — там же. На пилоте персональные данные появятся: клиенты-ИП (ФИО, ИНН физлица), подписанты УПД, логины
сотрудников. Для них — обработка в контуре банка по его политике 152-ФЗ; LLM их не получает (см. ниже).

## Карта обработки данных

Каждая стрелка — что передаётся, зачем, кому, на каком основании и сколько хранится. В карте не только основная база:
логи, браузер, сертификаты, хостинг и CI — тоже маршруты данных.

```
              сотрудник банка (браузер)                                   ┌──────────── вне контура ───────────────┐
                   │ ① HTTPS: логин/пароль, токен                         │ ⑨ GigaChat: тексты с метками (Р-73)    │
                   ▼                                                      │ ⑩ Let's Encrypt: имена хостов          │
  ┌──────── VDS стенда (хостинг) / контур банка на пилоте ────────┐       │ ⑪ sslip.io: DNS-имя с IP стенда        │
  │ Caddy (TLS) ─▶ UI ─▶ gateway ─▶ backend ─▶ ml (оценки)        │       │ ⑫ GitHub: код, образы, секреты стенда │
  │                  ② Keycloak ◀┘    │  ├──▶ ③ PostgreSQL         │──────▶└────────────────────────────────────────┘
  │                                   │  └──▶ ④ LLM в контуре      │
  │  ⑤ логи контейнеров (Docker)      │                            │
  │  ⑥ загрузка данных: ZIP оператора → временный каталог          │
  └───────────────────────────────────────────────────────────────┘
```

| № | Маршрут | Что передаётся | Зачем | Получатель | Основание | Сколько хранится |
|---|---|---|---|---|---|---|
| ① | браузер → Caddy → UI / gateway / Keycloak | логин и пароль (только Keycloak), токен, запросы API, ответы с данными клиентов | работа пользователя | система (стенд или контур банка) | трудовые обязанности работника банка | токен в sessionStorage вкладки до закрытия, 15 минут жизни; в браузере данные не сохраняются |
| ② | gateway → Keycloak | ключи проверки подписи токенов | проверка пользователя | Keycloak | — (персональных данных нет) | — |
| ③ | backend → PostgreSQL | загрузки, клиенты, покупатели, УПД, оценки, предложения, решения менеджеров, журнал, кеш текстов LLM | расчёт и аудит | база стенда | поручение банка (на пилоте) | до очистки данных; на пилоте — по сроку банка |
| ④ | backend → LLM в контуре (`LLM_MODE=onprem`) | факты карточки с метками вместо названий и ИНН | текст объяснения и черновик сообщения | сервер моделей банка | поручение банка | сервер моделей не хранит запросы (настраивает банк) |
| — | backend → ml | ИНН и отчётность покупателей, УПД (суммы, даты, номер), ИНН и отрасль клиента | PD и вероятность задержки | сервис моделей (тот же контур) | поручение банка | не хранит: запрос в памяти, в лог — только метод, путь, код, время |
| ⑤ | все контейнеры → логи Docker | логины, номера запусков, отказы в доступе, номер УПД при сбое LLM; IP-адрес посетителя на каждый запрос (access-лог gateway, без последнего октета) и при неудачном входе (Keycloak) | разбор сбоев, аудит доступа | VDS (на пилоте — SIEM банка) | — | ротация: 5 файлов по 10 МБ на сервис |
| ⑥ | оператор → backend: ZIP выгрузки или events.csv | исходные данные партии | загрузка данных | временный каталог контейнера backend | поручение банка | удаляется сразу после импорта (`ManualUploadService`), в т.ч. при ошибке |
| ⑦ | gateway → backend → журнал | кто запускал анализ, кто принял решение, отказы в доступе | аудит (НФР-7) | база и логи | — | как ③ и ⑤ |
| ⑧ | Keycloak → его база | пользователи, хеши паролей, сессии, неудачные входы (защита от подбора) | вход | база `keycloak` (тот же Postgres) | трудовые отношения (банк) | до удаления пользователя; сессия — до 10 часов |
| ⑨ | backend → GigaChat (`LLM_MODE=gigachat`) | факты карточки с метками `CLIENT_1`, `BUYER_1`, `INN_1`, `UPD_1`; суммы, даты, уровень риска | текст объяснения | ПАО Сбербанк (GigaChat API), РФ | решение банка; персональных данных не передаётся | по условиям GigaChat API (см. [«Внешние получатели»](#внешние-получатели)) |
| ⑩ | Caddy → Let's Encrypt | имена `app.`, `api.`, `auth.<домен>` | сертификат TLS | ISRG (США) | — (персональных данных нет) | имена публикуются в журналах Certificate Transparency навсегда |
| ⑪ | браузер → DNS sslip.io | имя хоста с IP стенда | адрес стенда без своего домена | sslip.io | — | по политике сервиса; данных клиентов нет |
| ⑫ | разработчик / CI → GitHub, ghcr.io | код, образы, секреты окружений, логи сборок | разработка и выкат | GitHub (США) | — (данных клиентов нет) | бессрочно (код публичный); секреты — до удаления |
| — | резервные копии | не делаются на стенде: данные — синтетика, восстанавливаются повторной загрузкой | — | — | — | — |

На пилоте маршруты ⑩–⑫ к данным клиентов отношения не имеют, ⑨ — только по решению банка, ⑪ не используется (свой
домен банка).

## Цель каждого поля и минимизация

Поля, которые уходят за пределы базы — в сервис моделей и в LLM. Принцип: собирать поле в момент, когда оно нужно, и
только туда, где у него есть цель.

| Поле | Цель | Куда уходит | Решение |
|---|---|---|---|
| ИНН покупателя | ключ отчётности и истории оплат покупателя | ml | нужно; открытые данные |
| ОКВЭД, регион, дата регистрации покупателя | признаки модели PD | ml | нужно |
| Отчётность покупателя (строки баланса и ОФР) | признаки модели PD | ml | нужно; открытые данные ГИР БО |
| УПД: сумма, остаток, даты, отсрочка | признаки модели задержки | ml | нужно |
| Номер УПД | порядок УПД одного дня в истории пары клиент–покупатель | ml | нужно; в LLM — меткой `UPD_1` |
| ИНН клиента | ключ пары клиент–покупатель в модели задержки | ml | **обосновано, на пилоте заменить**: модели нужен только идентификатор, а у клиента-ИП ИНН — персональные данные. Замена на внутренний ключ затрагивает заглушку моделей и эталонные тесты — сделать до допуска реальных данных (владелец — команда backend и ML) |
| Отрасль клиента | признак модели задержки | ml | нужно |
| Название клиента, название и ИНН покупателя | обращение в тексте карточки | LLM | только метками (Р-73), настоящие значения подставляет backend |
| Уровень риска, PD, сумма, цена, срок, причины оценки | содержание объяснения | LLM | нужно: без них объяснения нет; по ним клиента не узнать |
| ФИО подписанта УПД, ФИО клиента-ИП | — | никуда | не загружаются: в форматах загрузки их нет |
| Данные пользователей (логин, почта) | вход, журнал | Keycloak, журнал | не уходят ни в ml, ни в LLM |

## Роли сторон и правовые основания

| Сторона | Роль по 152-ФЗ | Что делает |
|---|---|---|
| Банк (ВТБ) | **оператор** персональных данных и держатель банковской тайны | определяет цели и основания, уведомляет Роскомнадзор, отвечает перед субъектами; уровень защищённости ИСПДн |
| Команда Smart Factoring (разработчик, сопровождение) | обработка **по поручению** оператора (ч. 3 ст. 6) | обрабатывает только по договору поручения и в его пределах |
| Хостинг (на стенде — SmartApe; на пилоте — инфраструктура банка) | на стенде — хранение синтетики; на пилоте не участвует | облако не принимает на себя обязанности оператора: меры защиты в приложении и ОС остаются за нами |
| GigaChat (ПАО Сбербанк) | получатель обезличенного текста; персональных данных не получает | только при `LLM_MODE=gigachat` и по решению банка |
| ВТБ Факторинг | получатель пакета по «Передать в факторинг» | отдельный оператор: своя обработка по своему основанию |

| Категория данных | Основание (на пилоте) | Чьё решение |
|---|---|---|
| Данные клиентов-юрлиц, УПД, платежи | договор банка с клиентом; согласие клиента на анализ данных ЭДО — **отдельный документ** (подписывается в ЭДО или в банке), а не галочка в интерфейсе; признак `edo_consent` в системе лишь отражает факт согласия | банк |
| Персональные данные клиентов-ИП и подписантов | согласие субъекта или исполнение договора (п. 1, 5 ч. 1 ст. 6 152-ФЗ) — определяет банк | банк |
| Данные работников (логины) | трудовые отношения | банк |
| Открытые данные о покупателях | общедоступные сведения ЕГРЮЛ, ГИР БО, ЕФРСБ | — |

**Что должно быть в договоре поручения** (ч. 3 ст. 6 152-ФЗ, для пилота): перечень персональных данных и действий с
ними, цели обработки; обязанность соблюдать конфиденциальность и меры по ст. 19 (раздел
[«Матрица применимости»](#матрица-применимости-требований)); обязанность по запросу банка подтверждать принятые меры и
уведомлять банк об инцидентах (раздел [«Инцидент»](#порядок-действий-при-инциденте)); место обработки — только
инфраструктура банка в РФ; завершение работы — удаление данных и отзыв доступов в срок с актом
([«Удаление»](#жизненный-цикл-данных-и-удаление), [«Доступы»](#реестр-доступов-и-их-отзыв)); запрет передачи третьим
лицам, кроме согласованных (GigaChat — только обезличенно).

## Внешние получатели

Пять вопросов воркшопа к каждому поставщику: что получает, где обрабатывает, сколько хранит, как удаляет, что при
инциденте.

| Получатель | Что получает | Где | Сколько хранит | Как удаляется | При инциденте |
|---|---|---|---|---|---|
| GigaChat API (ПАО Сбербанк) | тексты фактов карточки с метками вместо названий и реквизитов (Р-73) | РФ | по условиям GigaChat API; персональных данных и названий в запросах нет | у поставщика; у нас — кеш текстов удаляется очисткой данных | ключ `GIGACHAT_AUTH_KEY` отзывается в личном кабинете, `LLM_MODE=stub` — система работает без LLM |
| SmartApe (хостинг VDS стенда) | весь стенд: синтетика, учётные записи команды и гостя | РФ — **сверить по договору хостинга** (владелец стенда) | пока арендован VDS | удаление VDS с дисками после финала | смена паролей и ключей, пересоздание стенда из репозиториев |
| Let's Encrypt (ISRG) | имена хостов `app.`, `api.`, `auth.<домен>` | США | публично и навсегда (Certificate Transparency) | не удаляется — поэтому в именах нет названий клиентов и банка | не влияет на данные |
| sslip.io | DNS-запросы имён с IP стенда | вне РФ | по политике сервиса | — | заменить на свой домен |
| GitHub, ghcr.io | код (публичный), образы, секреты окружений, логи сборок | США | бессрочно | удаление репозиториев и секретов | секрет попал в git — проверка gitleaks (Р-77), смена секрета |

**Трансграничная передача персональных данных отсутствует**: Let's Encrypt и sslip.io получают только имена хостов,
GitHub — код и технические секреты стенда (не персональные данные), GigaChat находится в РФ и получает обезличенный
текст. Уведомление Роскомнадзора о трансграничной передаче (ст. 12 152-ФЗ) не требуется.

## Кто что видит

```
браузер ──Keycloak (OIDC, PKCE; оператор, руководитель - с OTP)──▶ токен
   └─ /api/** + Bearer ──▶ ui (nginx) ──▶ gateway ──▶ backend ──▶ ml
                                         │ подпись, issuer, срок токена;
                                         │ роли на путях; LLM закрыта всем
                                         └─ без токена - 401, до backend не доходит
```

| Роль | Что доступно |
|---|---|
| `operator` | экран процесса: загрузка данных, запуск анализа, результаты, журнал — по всем клиентам |
| `manager` | эмулятор CRM: очередь, карточки, уведомления, «Передать» / «Отклонить» — **только по своим клиентам** (НФР-9, Р-75); экран процесса — тоже только свои клиенты: детализация УПД, воронка, клиенты и покупатели запуска, журнал (Р-79) |
| `supervisor` | руководитель: эмулятор CRM по всем менеджерам и прогоны — только просмотр, решения по предложениям принимает менеджер (gateway) |
| гостевой вход «Запуск демо» | всё только для просмотра: изменяющие запросы отклоняет gateway |
| никто | `/api/backend/llm/**` — LLM пользователю напрямую не доступна (Р-80): в модель уходят только данные, которые собирает сам backend |

- Токен проверяет gateway (ключи realm Keycloak, issuer, срок). Backend и сервис моделей наружу не опубликованы и
  доступны только из сети стенда.
- «Успешно войти — не значит получить все права»: backend проверяет не только роль, но и конкретный объект. Чей
  менеджер пользователь — по claim `manager_codes` токена: атрибут пользователя `manager_code` в Keycloak, меняет только
  администратор (Р-90; на пилоте — IAM банка). Чужая карточка, предложение или
  путь чужого УПД — `403`, отказ пишется в лог backend. Списки (УПД, клиенты, покупатели, журнал) фильтруются в SQL.
- Снаружи — только HTTPS (Р-78): `app.`, `api.`, `auth.` в домене стенда за TLS-прокси; админка Keycloak из интернета
  закрыта, только через SSH-туннель.
- Postgres доступен только внутри Docker-сети и на `127.0.0.1` сервера (для IDE через SSH-туннель). У каждого стенда
  своя база и пользователь, чужие базы ему недоступны.

## Размещение в контуре банка (пилот)

Все компоненты — контейнеры без облачных зависимостей: тот же набор, что на стенде хакатона, разворачивается в
Kubernetes или на виртуальных машинах банка. Обязательного доступа в интернет нет.

```
контур банка (наружу - ничего; по желанию банка - GigaChat API с маскированием, Р-73)
│
├─ DMZ: WAF / балансировщик банка          ◀── HTTPS ── сотрудник (браузер)
│        (на стенде - Caddy, Р-78)
│
├─ зона приложений
│    UI ──▶ gateway ──▶ backend ──▶ сервис моделей (PD, задержка)
│             │            ├──▶ LLM в контуре (vLLM, LLM_MODE=onprem)
│             │            └──▶ интеграции банка: ЭДО, выписки, CRM,
│             │                 проверка контрагентов, ВТБ Факторинг
│             └──▶ IAM банка (OIDC; вместо Keycloak стенда)
│
└─ зона данных
     PostgreSQL (Postgres Pro), резервные копии - средствами банка
```

| Что | На стенде хакатона | В контуре банка |
|---|---|---|
| Вход пользователей | Keycloak стенда, роли `operator`, `manager`, `supervisor`, OTP для оператора и руководителя | IAM банка по OIDC: те же роли, второй фактор банка, закрепление клиентов за менеджером — из CRM |
| Внешний трафик | Caddy, сертификаты Let's Encrypt | WAF и сертификаты банка |
| LLM | GigaChat или заглушка | LLM в контуре или GigaChat по решению банка; маскирование включено в обоих случаях |
| Данные о покупателях | снимок открытых данных (RFSD, ЕГРЮЛ, ЕФРСБ) | сервисы данных банка; обновление без выхода приложения в интернет |
| Источники клиента | имитации, ручная загрузка партий | адаптеры к ЭДО, выпискам, CRM вместо имитаций (интерфейсы уже разделены) |

## LLM: что уходит наружу

LLM пишет менеджеру объяснение оценки и черновик сообщения клиенту. Решение (предлагать или нет, сумма, цена) LLM не
принимает: его считает код по правилам BRD. «Модель не должна решать, кому доступны данные»: пользователь не обращается
к LLM напрямую (Р-80), запрос собирает backend из фактов карточки, доступной этому пользователю.

| Защита | Как работает |
|---|---|
| Маскирование (Р-73) | В LLM вместо названия клиента, названия и ИНН покупателя и номера УПД уходят метки `CLIENT_1`, `BUYER_1`, `INN_1`, `UPD_1`; настоящие значения backend подставляет в ответ. Любые числа длиной ИНН и ОГРН в любом запросе к LLM тоже заменяются метками. Суммы, даты и уровень риска остаются: по ним одним клиента не узнать. Включено по умолчанию (`LLM_MASK=true`) |
| LLM в контуре (Р-74) | `LLM_MODE=onprem`: сервер с API вида OpenAI в сети банка (vLLM, Ollama) и открытая модель (T-lite / T-pro, GigaChat Lite, Qwen). Данные не покидают контур. Рассуждение моделей с «мышлением» (`<think>`) менеджеру не показывается |
| Российская облачная LLM | `LLM_MODE=gigachat`: GigaChat API, TLS с корневым сертификатом НУЦ Минцифры |
| Нет прямого доступа (Р-80) | `/api/backend/llm/**` в gateway закрыт всем ролям и гостю; сервис моделей обращается к backend по сети стенда |
| Проверка ответа (Р-59) | Ответ с оценками или обещаниями, которых нет во входных фактах, или с искажённой меткой — повтор, затем шаблонный текст. Менеджер видит источник текста (LLM, кеш, шаблон) |
| Без LLM | `LLM_MODE=stub` или `off`: шаблонные тексты, система работает полностью |

Сервис моделей (PD, задержка) — свой код в контуре, внешних вызовов не делает; к LLM ходит только через backend, с
тем же маскированием.

и Deploy, отзыв доступов по [реестру](#реестр-доступов-и-их-отзыв), удаление VDS с дисками.

## Пароли и второй фактор

Утечки чаще всего — человеческий фактор: слабый пароль администратора, фишинг. Меры (`security-setup.sh` в
smart-factoring-deploy, README «Пароли и второй фактор»):

| Мера | Где | Проверка |
|---|---|---|
| Политика паролей: от 12 символов, заглавные и строчные буквы, цифры, не совпадает с логином и почтой, не повторяет 3 последних | realm стенда (и в realm-файле) и master | локально на Keycloak 26.8.1 и 26.8.2, 21.11.2026: пароль `demo12345` отклонён («minimum length 12») |
| Обязательный OTP (приложение-аутентификатор) при входе через браузер для `operator` и `supervisor` | realm стенда: копия browser flow с условием по роли `otp-required`, она входит в обе роли | там же: оператор при входе получает «Mobile Authenticator Setup», менеджер входит без кода |
| Обязательный OTP для администратора Keycloak | master | там же: администратор получает настройку OTP |
| Защита от подбора, короткие токены, нет самостоятельной регистрации | realm | конфигурация realm |
| Вход без браузера не меняется: гость (gateway), `kcadm` | — | там же: гость получает токен (200) |

Пароли, заданные до политики, Keycloak не перепроверяет: смена паролей администратора, тестового и демо-пользователя
на стенде — за владельцем стенда (README, шаг 2). На стенде скрипт ещё не запускался.

  из репозитория и сменить сам секрет, он уже в истории публичного репозитория.

  `.env`. Найден один случай — `.env` с логином и паролем администратора локальной Postgres разработчика (порт 5433)

  разработчика и подлежит смене везде, где используется. В локальном `test.env` стенда test его нет; секреты стендов
  в GitHub (`POSTGRES_PASSWORD_ADMIN` и др.) владелец проверяет сам. Историю git не переписываем: репозитории публичные
  и уже склонированы, переписывание не отзывает утёкший пароль — отзывает только его смена.

## Порядок действий при инциденте

Инцидент — неправомерный доступ к данным, их утечка, изменение или уничтожение, а также компрометация учётной записи
или секрета.

| Шаг | Кто | Что делает | Срок |
|---|---|---|---|
| 1. Выявление | любой участник команды; сигналы: отказы в доступе в логах gateway и backend, красная проверка gitleaks, сообщение пользователя | сообщает владельцу стенда (на пилоте — дежурной службе ИБ банка) | сразу |
| 2. Сдерживание | владелец стенда | отзывает скомпрометированный доступ ([реестр](#реестр-доступов-и-их-отзыв)), меняет секрет, при необходимости останавливает стенд или `LLM_MODE=stub` | в течение часа |
| 3. Решение | на стенде — владелец стенда; на пилоте — банк (оператор) | оценивает, затронуты ли персональные данные и банковская тайна | — |
| 4. Уведомление | на пилоте мы как обработчик уведомляем **банк**; Роскомнадзор уведомляет **оператор — банк** (ч. 3.1 ст. 21 152-ФЗ) | первичное уведомление: что случилось, предполагаемые причины, вред, принятые меры, контакт | **24 часа** с момента выявления |
| 5. Расследование | команда вместе с ИБ банка | причины, виновные, результаты | **72 часа** с момента выявления — результаты расследования (оператор — в Роскомнадзор) |
| 6. Восстановление и выводы | команда | исправление, новая проверка в CI или тест, запись в этот документ | — |

На стенде хакатона персональных данных нет (синтетика), уведомление Роскомнадзора не требуется; порядок отрабатывается
на стенде, чтобы на пилоте он был привычным. Контакты: на стенде — владелец репозиториев (GitHub), на пилоте —
контакт ИБ банка, указанный в договоре поручения.

## Для презентации (1 слайд)

**Данные клиентов не покидают контур банка — и это проверено**

- Демо — только открытые данные о компаниях и синтетика; реальные данные — после чек-листа «данные, основание,
  маршруты, права, завершение, проверка».
- Банк — оператор, мы — по поручению; согласие на анализ ЭДО — документ, а не галочка; персональные данные за
  границу не уходят.
- LLM получает метки вместо названий, ИНН и номеров документов; пользователю модель напрямую недоступна; можно
  полностью в контуре (`LLM_MODE=onprem`).
- Менеджер видит только своих клиентов на всех экранах; оператор и руководитель входят с одноразовым кодом.
- Каждый push — SAST, проверка зависимостей и образов, поиск секретов; найденные CRITICAL уже исправлены.
- Удаление — по всем копиям, доступы — с владельцем и сроком отзыва; инцидент — 24 / 72 часа через банк.

Схема для слайда — «Карта обработки данных» и «Размещение в контуре банка» выше; подробности — этот документ (PDF —
`Smart_Factoring_Security.pdf` в аналитике загрузки).
